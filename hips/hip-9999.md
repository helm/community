## Abstract

This HIP proposes adding [Sigstore][sigstore] "keyless" signing for Helm releases alongside the existing PGP signatures.
The release workflow will sign each release archive with [cosign][cosign signing], and the resulting signatures are both published to `get.helm.sh` and attached to GitHub releases.
Helm's installer scripts will verify the signatures by default when `cosign` is available, warning the user when not.
The existing PGP signing process remains unchanged.

## Motivation

### Helm is a high-value supply-chain target

Helm is widely used, heavily distributed (from `get.helm.sh` on the order of terabytes per month), and runs with Kubernetes credentials (often with cluster-admin privileges).
A distribution compromise would reach many clusters with privileged access: release verification must be practical and should be enabled by default.

Today, it is neither.
Helm's PGP signatures (`.asc`) are attached to GitHub releases rather than served alongside the archives on `get.helm.sh`.
Verifying them means fetching the signatures and the `KEYS` file from GitHub, a separate channel subject to GitHub's rate limits, then using `gpg`.
The installer scripts disable PGP verification by default and support it only on Linux.

Consequently, few users verify Helm binaries, and default installs have no provenance check at all.
Sigstore signing of `get.helm.sh` artifacts has been requested since 2022 ([helm/helm#10634][issue-10634], [helm/helm#10644][issue-10644]).

### Limitations of PGP for release signing

Security practitioners have long criticized PGP for its complexity, poor usability, and reliance on long-lived keys ([The PGP Problem][pgp-problem]).
For Helm, this means:

1. **Long-lived secrets:** Each release manager must keep a personal private key secret *for years*. For most maintainers, this means the key resides on a personal development machine — a significant risk.
2. **An ever-growing `KEYS` file:** Release managers sign releases with individual keys, so every release manager's key must remain in `KEYS` for past releases to stay verifiable. Most of those keys now belong to former maintainers.
3. **Retroactive loss of trust:** If a key is compromised, every past release signed with that key becomes suspect. Revocation also rarely reaches users in practice, because downstream keyrings are seldom refreshed ([Cohen][pgp-sigstore-post]).
4. **Trust is placed in individuals:** Verifiers must trust a set of personal keys, not the project's build process.
5. **Signing happens outside the build:** Signatures are made on a maintainer's machine after the release is built, so they attest to the maintainer, not to the workflow that built the artifact. Nothing ties a signature to the CI run, tag, or source commit that produced it.

This proposal adds a modern alternative alongside PGP, rather than attempting to improve Helm's PGP signing process, and leaves the existing PGP signing unmodified.

## Rationale

### Why Sigstore "keyless" (identity-based) signing

Sigstore addresses the PGP limitations above by changing how signing keys are managed and trusted, rather than by changing the underlying cryptography:

1. **Ephemeral keys.** Each signing operation uses a short-lived key that is discarded after use. There is no long-lived secret to store, rotate, or protect, and unlike a PGP key, a discarded key cannot later be stolen and used to forge signatures for past releases.
2. **Identity-based trust.** Signatures are bound to the identity of the `helm/helm` release workflow for a specific tag, not an individual maintainer (see [Why sign in CI](#why-sign-in-ci-verifiable-build-provenance)).
3. **Transparency.** Each signature is recorded in the public, tamper-evident [Rekor][rekor] transparency log. Unexpected signatures made with Helm's identity can be detected by monitoring the log, for example a signature produced by re-triggering the release workflow for an existing tag. PGP signatures leave no such record.
4. **Simpler verification.** Users verify against a documented identity (repository, workflow, and tag), instead of curating a keyring of maintainer keys.

[Kubernetes][k8s-signing], CPython ([PEP 761][pep-761]), and [npm][npm-provenance] all use Sigstore for release provenance, and [GoReleaser supports it natively][goreleaser-sign].

### Why sign in CI: verifiable build provenance

GitHub Actions issues each workflow run a short-lived OIDC token, signed by GitHub, whose [claims][github-oidc] describe the run: the repository, the workflow file and its commit, the git ref (for example `refs/tags/v4.2.0`), the source commit SHA, the triggering event, and the run ID.
Sigstore's certificate authority ([Fulcio][fulcio]) copies these claims into the signing certificate as [X.509 extensions][fulcio-oids], and the certificate is recorded in the Rekor transparency log with the signature.

Each Helm release signature therefore carries a GitHub-attested, publicly logged record of which workflow run, at which tag and commit, produced the artifact.
Verifiers can check these claims directly (for example, with `cosign verify-blob --certificate-github-workflow-sha`), rather than only checking that a trusted key signed the artifact.
A PGP signature cannot carry this information, wherever its key is held (see [Rejected ideas](#rejected-ideas)).

### Why publish to both `get.helm.sh` and GitHub

Historically, there has been no facility to publish signatures to `get.helm.sh`.
Signing was a manual step on the release manager's machine, and release managers (correctly) do not have direct upload access to the `get.helm.sh` storage backend.
Signing within the release workflow removes this constraint.

Publishing to `get.helm.sh` places each signature next to the archive it covers, so the installer scripts can fetch both from the same location without running into GitHub's rate limits ([helm/helm#12351][issue-12351]).
Attaching the signatures to the GitHub release keeps them alongside the existing `.asc` files and provides a second, independent copy.

### Why verify by default in the installer scripts

Signatures add value only when users verify them, and opt-in verification is rarely used.
Most users install Helm through the installer scripts, so verifying there by default protects most installs without any action from users.
Requiring `cosign` would break existing environments, such as CI pipelines that run `curl | bash`, so the scripts verify when `cosign` is present and warn when it is not.
A signature that fails verification, however, indicates possible tampering, so the scripts abort instead of continuing.

## Specification

### Scope

In scope:

- Signing official release archives with Sigstore in the release workflow.
- Publishing the signatures to `get.helm.sh` and to GitHub releases.
- Verifying signatures in the Helm installer scripts.

Out of scope:

- Deprecating, replacing, or modifying the PGP signing process, the `KEYS` file, `.asc` files, or the installer's existing PGP verification logic.
- Publishing Helm binaries to GitHub releases.
- SBOMs and SLSA build provenance attestations.
- Signing or verifying Helm charts or plugins with Sigstore. This HIP covers Helm's own release artifacts only. Chart provenance (`helm package --sign`, `helm verify`) is unchanged.

### Signing

For every tagged Helm release, the official release workflow:

1. Builds and packages the release archives (`helm-<tag>-<os>-<arch>.tar.gz` / `.zip`) as done today.
2. Signs each archive with `cosign` in keyless mode, using the release workflow's GitHub Actions OIDC identity. Each signature is recorded in the public Rekor transparency log.
3. Writes a [Sigstore bundle][sigstore-bundle] for each archive, named `<archive>.sigstore.json`. The bundle contains the signature, the signing certificate, and the transparency log inclusion proof.

Signing runs in the same release workflow run, on the same files that are uploaded to `get.helm.sh`. If signing fails, the release fails.

### Publishing

Each `.sigstore.json` bundle is published:

1. To `get.helm.sh`, next to its archive:
   ```
   https://get.helm.sh/helm-v4.2.0-linux-amd64.tar.gz
   https://get.helm.sh/helm-v4.2.0-linux-amd64.tar.gz.sigstore.json
   ```
2. As an asset on the corresponding GitHub release, alongside the existing `.asc` files. The release workflow also attaches the signature bundles to the GitHub release. Release archives are not uploaded to GitHub.

### Verification identity

A valid signature must have:

| Property | Value |
| --- | --- |
| OIDC issuer | `https://token.actions.githubusercontent.com` |
| Certificate identity | The `helm/helm` release workflow at ref `refs/tags/<tag>` |

The exact identity string will be documented on `helm.sh`. Manual verification looks like this:

```sh
cosign verify-blob \
  --bundle helm-v4.2.0-linux-amd64.tar.gz.sigstore.json \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity "https://github.com/helm/helm/.github/workflows/<release-workflow>@refs/tags/v4.2.0" \
  helm-v4.2.0-linux-amd64.tar.gz
```

Pinning the tag in the identity means a signature for one release cannot be presented as valid for another.

### Installer scripts

The installer scripts verify the Sigstore signature of the downloaded archive before installing it.
The signature bundle is downloaded from `get.helm.sh`, not GitHub, so verification adds no exposure to GitHub rate or bandwidth limits.

Verification is controlled by the existing `VERIFY_SIGNATURES` environment variable. Its default changes from `false` to `auto`:

| `VERIFY_SIGNATURES` | PGP | Sigstore | Notes |
| --- | --- | --- | --- |
| `auto` (default) | Skip | Verify if `cosign` is installed | New default |
| `true` | Verify | Verify if `cosign` is installed | Today's PGP verification, extended with Sigstore |
| `pgp` | Verify | Skip | Same behavior as today's `true` |
| `sigstore` | Skip | Verify; `cosign` required | Strict, Sigstore only |
| `false` | Skip | Skip | Opts out of all signature verification |

When Sigstore verification applies, the scripts behave as follows:

| Condition | `auto` / `true` | `sigstore` |
| --- | --- | --- |
| `cosign` not installed | Warn that the signature was not verified, with a link to the verification docs. Continue. | Abort. |
| Bundle present, verification succeeds | Continue. | Continue. |
| Bundle present, verification fails | Abort, with a link to `SECURITY.md`. | Abort, with a link to `SECURITY.md`. |
| Bundle missing, and the release predates the first signed release (or is `canary`) | Warn that the release is unsigned. Continue. | Abort. |
| Bundle missing, and the release is the first signed release or later | Abort, with a link to `SECURITY.md`. | Abort, with a link to `SECURITY.md`. |

The installer embeds the first signed release version to make this distinction.
Aborting when the bundle is missing for a release that should be signed prevents an attacker who can modify `get.helm.sh` from bypassing verification by deleting the signature.

This section specifies the intended end state.
Implementations may stage it, for example by keeping `false` as the default until confidence in `cosign` verification is established, or by warning instead of aborting on verification failure as an interim step (see [Open issues](#open-issues)).

The scripts must not install `cosign` or any other dependency.

## Backwards compatibility

Signing and publishing are purely additive: existing artifacts, checksums, URLs, and PGP signatures are unchanged.

The installer script changes are a **potential breaking change**, taking effect when the default changes to `auto`.
Under the new `auto` default, an install that succeeds today aborts if `cosign` is installed and verification fails or a required bundle is missing.
Verification can also fail for reasons unrelated to tampering, for example when `cosign` cannot reach Sigstore's trust root in an air-gapped or proxied environment.
Users who set `VERIFY_SIGNATURES=true` also gain Sigstore verification in addition to PGP.
Users can restore today's behavior with `VERIFY_SIGNATURES=false` (the previous default) or `VERIFY_SIGNATURES=pgp` (the previous `true`).

Maintainers generally read [HIP-0004][hip-0004] as a broad promise of stability across the Helm ecosystem, including the installer scripts.
Whether failing closed by default is acceptable is recorded as an open issue.

## Security implications

Sigstore signing is a new trust path for Helm release provenance, so it warrants careful security review.

Benefits:

- **Installer integrity validation by default:** moving the installer to `VERIFY_SIGNATURES=auto` as the default immediately protects users with `cosign` installed (and users without are warned). Currently, Helm installer users have no tamper protection (by default).
- **Provenance tied to the build, not a person:** PGP signatures show that *a* maintainer signed an artifact. Sigstore signatures show that the artifact was produced by the `helm/helm` release workflow for that release tag.
- **Reduced reliance on PGP:** users can verify release provenance without PGP, without managing a keyring, and without trusting individual maintainers' long-lived keys.
- **No new long-lived secret:** Sigstore requires no new persistent signing key to be stored by Helm's release CI.

Risks:

- **Release workflow integrity:** anyone who can push a `v*` tag or modify the release workflow (including its pinned third-party actions) can produce validly signed artifacts: a signature is only as trustworthy as the release workflow. Tag protection and workflow review therefore form part of the trust boundary. Unexpected signatures may be detected by monitoring the transparency log.
- **Third-party trust:** verification depends on GitHub's OIDC issuer and on Sigstore's public-good infrastructure (Fulcio, Rekor, and its trust root).
- **Availability:** Sigstore must be reachable at signing time, otherwise the release fails. At verification time, `cosign` needs the bundle and Sigstore's trust root.
- **Partial coverage:** users without `cosign` gain no provenance verification, and the installer warns them that the signature was not verified.
- **Signatures share an origin with the archives:** an attacker who controls `get.helm.sh` cannot forge a signature, but can delete one. The installer aborts when a bundle is missing for a release that should be signed, and the verification docs instruct users to treat a missing bundle as a failure.

## How to teach this

The <https://helm.sh/docs/intro/install/> docs should include:

- A Sigstore "Verifying Helm releases" section, leading with the `cosign verify-blob` example and documenting the exact certificate identity.
- The `VERIFY_SIGNATURES` values and the optional `cosign` dependency.

The release checklist should also be updated to reflect that the release workflow attaches the Sigstore bundles to the GitHub release.

## Reference implementation

None yet. [helm/helm#32490][pr-32490] is prior work, but it signs a separate build published to GitHub releases, which this proposal rules out.

## Rejected ideas

- **Publishing binaries to GitHub releases and signing those:** GitHub rate and bandwidth limits make it unsuitable as the primary distribution channel. Signatures from a separate build would not match the `get.helm.sh` archives.
- **Signing with Sigstore only (dropping PGP):** not proposed by this HIP. Some users and downstream packagers depend on PGP signatures today; deprecating PGP signing is left to a follow-up HIP.
- **PGP signing in CI:** a PGP signature proves only possession of a key, and cannot attest which workflow, commit, or tag produced the signed artifact.
  It would also place a long-lived key alongside the `get.helm.sh` upload credentials, where an attacker who exfiltrates both could silently replace and re-sign releases, _with no public record_.
  HashiCorp's 2021 exposure of its CI-held PGP release-signing key shows that this risk is real ([HCSEC-2021-12][hcsec]).
- **A key-based `cosign` signature:** this brings back long-lived key management, which keyless signing removes.
- **Installing `cosign` automatically from the installer script:** this would make the installer download and run another binary, which has its own trust problem.

## Open issues

- Should the archives be signed individually (as proposed), or should a single checksums manifest be signed instead?
- Should canary builds also be signed?
- When should the default change to `auto`, and should the installer then fail closed on Sigstore verification failure (as specified) or only warn, given the broad reading of HIP-0004? See [Backwards compatibility](#backwards-compatibility).
- How should the installer distinguish a verification failure from an inability to verify (for example, when Sigstore's trust root is unreachable)?
- Should signing be backported to the Helm 3 release branch and `get-helm-3`?
- Should existing releases be signed retroactively? Such signatures would attest only that Helm's CI vouched for the artifacts at the time of re-signing, not to the original build.
- Should Helm monitor Rekor for unexpected signatures under its release identity (for example, with `rekor-monitor`), and who responds to alerts?
