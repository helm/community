## Abstract

Helm's separate levels of maintainership introduce governance complexity and restrict access to shared project resources.
This proposal establishes a single level of maintainership with delegated responsibilities.

## Motivation

The distinction between project and Org maintainers creates unnecessary administrative overhead,
limits participation in project-wide decisions, and complicates access to shared resources and services.

All active Helm maintainers already contribute to the project and should be able to participate in its governance.

## Rationale

A single level of maintainership simplifies governance while preserving distributed technical decision-making.
Administrative and security responsibilities can be delegated without requiring a separate level of maintainership
or granting additional governance authority.

## Specification

Update [Helm governance](../governance/governance.md) as follows:

- Remove the Org maintainer role, associated elections, and chair.
- Establish a single level of maintainership, conferred through maintaining at least one active (non-archived) project.
- Give each active Helm maintainer one vote on organization-wide decisions, excluding triage and emeritus maintainers.
- Preserve project-specific technical decision-making and escalation to all Helm maintainers.
- Apply the existing employer diversity requirement to all Helm maintainers.
- Establish a minimum voting period of three business days, with voting thresholds calculated against all eligible maintainers.
- Establish delegated teams for specific responsibilities without conferring additional governance authority.
- Establish Helm Admins, initially comprising the existing Org maintainers,
  with appointments and removals requiring a super-majority vote.
- Define administrative responsibilities, including emergency action with subsequent reporting.
- Preserve the existing Security Team responsibilities and membership process.
- Require explicit ownership of all active repositories.
- Establish Helm Admin responsibility for verifying required governance approvals before merging protected changes.
- Maintain authoritative membership and ownership records without duplication.

These changes supersede the Org maintainer provisions of [HIP-0005](hip-0005.md)
and retain the maintainer group structure established by [HIP-0007](hip-0007.md).

### Implementation requirements

Before adopting the new governance:

- Obtain the required approvals under the existing governance.
- Assign the HIP number and update its status and index.
- Update affected documentation, policies, HIPs, membership records, and automation.
- Check dependencies and archive former Org-maintained repositories other than `helm/community`,
  which Helm Admins will administer on behalf of all maintainers.
- Verify explicit ownership of all remaining active repositories.
- Rename `@helm/helm-org-maintainers` to `@helm/helm-admins`, preserving membership and permissions.
- Configure and verify required Helm Admin code owner approval and repository protections
  before broadening repository write access.

As part of adoption:

- Update `helm/.project` metadata and the CNCF maintainers CSV.
- Verify maintainer access to applicable CNCF resources and services, preserving team-specific permissions.
- Preserve `helm-admin@lists.cncf.io` and other applicable mailing lists,
  and retire `cncf-helm-org-maintainers` after verifying replacement communication channels.

### Follow-up work

- Standardize membership records using structured data and GitHub usernames.
- Automate synchronization of maintainer and delegated team membership to `helm/.project`.

## Backwards compatibility

No existing active maintainer loses maintainership.
Existing administrative and security responsibilities are retained through delegated teams.
Changes to membership records, repository ownership, and shared resources are addressed by the implementation requirements.
