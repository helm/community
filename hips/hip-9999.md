## Abstract

For OCI dependencies, `Chart.yaml`'s `dependencies[].name` is forced to serve
two roles at once: the chart's identity (checked by `helm lint` against the
vendored subchart's own `Chart.yaml` `name`) and the basename Helm appends to
build the OCI pull reference (`oci://<repository>/<name>:<version>`). When a
chart is published or mirrored under a registry path whose basename differs
from its own `name` — common with registry mirroring or organization naming
conventions — there is no way to satisfy both roles. This HIP proposes an
optional `artifactName` field on `dependencies[]` entries that carries the OCI
pull basename separately from `name`, so `name` can always represent chart
identity.

## Motivation

### Current limitations

`helm dependency update` builds the OCI pull reference as
`oci://<repository>/<name>:<version>`, so `name` doubles as the registry
basename. `helm lint` separately requires `dependencies[].name` to match the
vendored subchart's own declared `name`. These uses conflict whenever a chart
is republished under a different OCI basename than its own identity.

### Real-world impact

Given `oci://example.com/org/dhi-metrics-server-chart:3.13.1` for a chart
whose own `Chart.yaml` declares `name: metrics-server-chart`, setting
`dependencies[].name` to the OCI basename lets `helm dependency update` pull
successfully, but `helm lint` then fails:

```text
[ERROR]   chart metadata is missing these dependencies: metrics-server-chart
[WARNING] chart directory is missing these dependencies: dhi-metrics-server-chart
```

This affects platform teams and CI/CD pipelines consuming charts through a
registry mirror or vendor naming convention they don't control.

### Existing workarounds

Users can vendor the chart manually into `charts/` and omit `repository`, but
that abandons `helm dependency update` entirely and requires a custom
fetch/vendor step maintained outside Helm.

This was reported and discussed in
[helm/helm#32529](https://github.com/helm/helm/issues/32529), which links
prior related discussions: #9627, #9386, #9278, #11127.

## Rationale

`name` keeps its existing meaning everywhere it's used today (lint, `charts/`
vendoring, alias/values wiring). A second, OCI-only field carries the pull
basename, opt-in and additive: dependencies that don't set it keep resolving
the pull basename from `name`, exactly as today.

### Why not overload `repository`

Allowing `repository` to be a full OCI reference (including the artifact
basename) would require every OCI-consuming code path to detect and strip a
trailing name segment, more invasive than one new field, and would change the
documented meaning of an existing field.

### Why not reuse `alias`

`alias` already has an established meaning — the values key a subchart is
addressed by — and is unrelated to OCI. Conflating it with the pull basename
would change existing, unrelated behavior for every chart already using
`alias`.

### Why per-dependency, not chart-level

A chart can have multiple OCI dependencies pulled from differently-named
artifacts, so the override must live on each `dependencies[]` entry.

## Specification

A new optional string field, `artifactName`, is added to `dependencies[]`
entries in `Chart.yaml`:

```yaml
dependencies:
  - name: metrics-server-chart
    artifactName: dhi-metrics-server-chart
    version: 3.13.1
    repository: oci://example.com/org
    alias: metrics-server
    condition: metrics-server.enabled
```

- `name` is unchanged: the chart's identity, matched against the vendored
  subchart's own `Chart.yaml` `name` by `helm lint`, and used to wire
  `alias`/values.
- `artifactName`, when set, is the basename used to build the OCI pull
  reference (`oci://<repository>/<artifactName>:<version>`) instead of `name`.
  It only affects OCI repositories; it has no effect for `http(s)` chart
  repositories or local (`file://`/subfolder) dependencies.
- If `artifactName` is empty or unset, the pull reference is built from `name`
  exactly as today.
- `helm dependency update` resolves the OCI tag/version and builds the pull
  reference using `artifactName` (falling back to `name`), downloads the
  artifact, and vendors it into `charts/` under the vendored chart's own
  declared name — unaffected by this change, since Helm already loads
  subcharts by their own `Chart.yaml` identity rather than by archive
  filename.
- `Chart.lock` records `artifactName` alongside `name` for each locked
  dependency, so `helm dependency build` (which reads the lock rather than
  re-resolving `Chart.yaml`) continues to pull the correct artifact.
- `helm lint` requires no behavior change: it already compares
  `dependencies[].name` to the vendored subchart's own name, with no
  OCI-specific logic. Once `name` is no longer forced to double as the OCI
  basename, the two values it compares naturally agree.

| Field set | Pull reference basename | `charts/` identity |
|---|---|---|
| `artifactName` unset | `name` | vendored chart's own `name` |
| `artifactName` set | `artifactName` | vendored chart's own `name` |

## Backwards compatibility

Fully additive and opt-in. Existing `Chart.yaml` files have no `artifactName`
field, so every dependency continues to resolve its OCI pull basename from
`name`, exactly as today. `Chart.lock` gains one new optional per-dependency
field, which older Helm versions reading a newer lock file simply ignore.
Non-OCI repositories and `helm lint` behavior for charts not using this field
are unaffected.

## Security implications

None identified. `artifactName` is sanitized the same way other
`dependencies[]` string fields are today, and is only ever used to construct
an OCI reference the same way `name` already is — it introduces no new class
of input reaching the registry client.

## How to teach this

This is an opt-in field relevant only to users publishing or consuming OCI
charts under a registry path whose basename differs from the chart's own
`name`. The `Chart.yaml` reference and the
[OCI dependencies guide](https://helm.sh/docs/topics/registries/#specifying-dependencies)
should document `artifactName` alongside `name`, `version`, and `repository`,
using the mirrored-registry scenario above as the motivating example.

## Reference implementation

A working reference implementation exists locally, covering
`pkg/chart/v2/dependency.go`, `pkg/downloader/manager.go`, and
`internal/resolver/resolver.go`, with unit and end-to-end test coverage. It
will be opened as a PR against `helm/helm` once this HIP is reviewed.

## Rejected ideas

- **Overload `repository` with a full OCI reference** — more invasive, and
  changes the meaning of an existing field (see Rationale).
- **Reuse `alias` for the pull basename** — `alias` already means "values
  key"; conflating it with OCI pull identity would be a breaking overload.
- **Chart-level (not per-dependency) override** — insufficient, since a chart
  can depend on multiple differently-renamed OCI artifacts.
- **Soften `helm lint` instead of adding a field** — lint is correctly
  reporting a real inconsistency in an underspecified model; papering over it
  would let `helm dependency update` silently vendor the wrong chart under
  the wrong declared identity.
